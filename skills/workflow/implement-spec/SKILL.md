# Implement Spec

仅在用户显式调用 `/implement-spec` 时执行；日常逐工单实现仍使用 `/implement`。

读取真实存在的 spec、关联工单及 `.adev/agents/issue-tracker.md`、`.adev/agents/verification.md`。缺少配置先提示用户运行 `/setup-devenv`；找不到 spec 时请用户指定，不以会话内容代替。目标是整份 spec 在一个集成分支上完成，工单全部经过用户验收与代码审查。

## 权威上下文与状态

工单组成依赖图。**frontier** 是所有阻塞工单均完成、且未被认领的工单；完成指整张 ticket 的清单验收与审查通过。

`.adev/` 被忽略，不会随 Git worktree 自动复制。开始时确定原工作区中 spec、工单、验证约定和领域文档的绝对路径，作为所有子 agent 共享的唯一权威副本；传递这些路径，不在各 worktree 创建副本。主 agent 独占工单状态、认领和完成记录的写入；子 agent 只读取并报告。验收清单与工单一同共享主工作区路径，通过勾选由用户填写。

子 agent 的任务以 spec、完整工单、集成分支提交和文档指针描述，不复制整份上下文。新分支使用项目约定的前缀。

## 执行

1. **建立基线。** 通读 spec、全部工单和依赖，确认每张 ticket 能独立编译并集中验收。宽重构采用 expand–contract；不能独立交付的工单先调整边界。记录审查基准，创建集成分支。

2. **派发一批工单。** 从当前 frontier 选择就绪 ticket，每张工单一次派发完整实现范围。给各实现子 agent 创建独立分支和 worktree，基于本批次开始时的集成分支提交。主 agent 记录认领；同一工单不重复派发。子 agent 读取共享绝对路径，实施整张 ticket 并编译，报告提交及清单草稿后停止。默认不新增测试项目、测试代码或自动化验收脚本；只有用户明确要求才新增，编译不能代替手动验收。

3. **集成并编译。** 主 agent 将本批工单逐一合入集成分支，解决冲突并编译。未编译通过时继续修复，不能请求用户验收或派发下一批。集成冲突改变行为时同时更新对应 ticket 的清单。

4. **交付清单。** 集成编译通过后，按 [清单约定](../check-result/references/acceptance.md) 为每张 ticket 生成独立 Markdown 验收清单，写入对应工单链接，注明集成分支的实际待验版本。整张 ticket 一次交付，状态改为 `awaiting-verification`；用户勾选通过项并记录问题。

5. **检查结果再推进依赖。** 用户更新清单后，主 agent 对相应 ticket 调用 `check-result`，传入真实 spec、工单、清单和准确累计 Git 范围。它判断待验证或继续修复，并在验收通过后调用 `code-review`。主 agent 统一落盘状态；只有标记 `done` 的工单才释放依赖，再计算 frontier 返回第 2 步。失败修复沿用原清单，仅复验受影响项。

6. **整体验证与交付。** 全部工单完成后，对集成分支相对起始基准做一次整体 `code-review`，检查跨工单配合与整份 spec。处理发现的问题，编译并在对应 ticket 的原清单更新受影响项，由 `check-result` 处理补验并复核审查。全部通过才完成 spec；调用 `commit-message` 为尚未提交的最终修复生成提交信息并提交。只有本次任务已授权创建 PR 时，才在首次有集成提交后创建草稿，最终验收与审查通过后标记可审查。在本地 spec 与工单文件记录完成状态并交付集成分支；PR 的发布与合并状态单独报告。

7. **清理。** 确认子 agent 的提交已集成，所需资料均留在权威位置，再清理本次创建的 worktree。报告分支、工单状态、编译结果和用户验收记录。
