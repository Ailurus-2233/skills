# Implement Spec

仅在用户显式调用 `/implement-spec` 时执行；日常逐工单实现仍使用 `/implement`。

读取真实存在的 spec、关联工单及 `.adev/agents/issue-tracker.md`、`.adev/agents/verification.md`。缺少配置先提示用户运行 `/setup-devenv`；找不到 spec 时请用户指定，不以会话内容代替。目标是整份 spec 在一个集成分支上完成，工单全部通过所需数据流测试、用户手动验收项与代码审查。

## 权威上下文与状态

工单组成依赖图。**frontier** 是所有阻塞工单均完成、且未被认领的工单；完成指整张 ticket 的清单验收与审查通过。

`.adev/` 被忽略，不会随 Git worktree 自动复制。开始时确定原工作区中 spec、工单、验证约定和领域文档的绝对路径，作为所有子 agent 共享的唯一权威副本；传递这些路径，不在各 worktree 创建副本。主 agent 独占工单状态、认领和完成记录的写入；子 agent 只读取并报告。验收清单与工单一同共享主工作区路径，自动化证据由主 agent 汇总，手动项勾选由用户填写。

子 agent 的任务以 spec、完整工单、集成分支提交和文档指针描述，不复制整份上下文。新分支使用项目约定的前缀。

同一工作目录的所有工单共用主工作区 `.adev/<类型>/<yyyy-mm>/<描述>/test/` 中的一个项目，不会随提交搬运。主 agent 独占共享项目的写入和运行；子 agent 只提交测试变更草稿及来源工单，不并发写共享文件或运行到共享输出目录。明确构造在单元测试项目中的测试随子分支集成。主 agent 合并测试变更后，对集成 checkout 串行执行本批新增用例及此前所有已验收工单的累计回归；记录被测代码、共享测试内容版本与报告。任何旧用例失败或未执行均阻止本批验收和依赖推进。

## 执行

主 agent 在本轮修改共享测试前保留可恢复的整体基线，并为每批记录修改前快照；两者都包含用例清单，修复保留原基线。整体审查使用本轮起始测试基线，批次审查使用相应快照。主 agent 在派发、集成、验收、修复和整体完成后统一刷新分类 ADR 的工作索引。

1. **建立基线。** 通读 spec、全部工单和依赖，确认每张 ticket 能独立编译并集中验收。宽重构采用 expand–contract；不能独立交付的工单先调整边界。记录审查基准，创建集成分支。

2. **派发一批工单。** 从当前 frontier 选择就绪 ticket，每张工单一次派发完整实现范围。给各实现子 agent 创建独立分支和 worktree，基于本批次开始时的集成分支提交。主 agent 记录认领；同一工单不重复派发。子 agent 读取共享绝对路径，实施整张 ticket 并编译，报告提交及清单草稿后停止。按共享验证配置的用户选择提供后台数据流测试变更草稿，由主 agent 合入共享项目并执行；客户端操作保留用户手动验收。配置缺少选择时由主 agent 收集并保存，子 agent 不自行设定。

3. **集成并编译。** 主 agent 将本批工单逐一合入集成分支，解决冲突并编译，启用自动化时在集成版本运行本批新增用例及此前所有已验收工单的累计回归。构建或所需测试未通过时继续修复，不能请求用户验收或派发下一批。集成冲突改变行为时同时更新对应 ticket 的清单。

4. **交付清单。** 集成构建及所需数据流测试通过后，按 [清单约定](../check-result/references/acceptance.md) 为每张 ticket 生成独立 Markdown 验收清单，写入对应工单链接，注明集成分支的实际待验版本。整张 ticket 一次交付，状态改为 `awaiting-verification`；用户勾选通过项并记录问题。

5. **检查结果再推进依赖。** 用户更新手动项后（纯后台工单可在自动化证据齐备后），主 agent 对相应 ticket 调用 `check-result`，传入真实 spec、工单、清单和准确累计 Git 范围。它判断待验证或继续修复，并在验收通过后调用 `code-review`。主 agent 统一落盘状态；只有标记 `done` 的工单才释放依赖，再计算 frontier 返回第 2 步。失败修复沿用原清单，手动项仅复验受影响部分，自动化重跑累计回归。

6. **整体验证与交付。** 全部工单完成后，对集成分支相对起始基准做一次整体 `code-review`，检查跨工单配合与整份 spec。处理发现的问题，编译并在对应 ticket 的原清单更新受影响项，由 `check-result` 处理补验并复核审查。全部通过才完成 spec；调用 `commit-message` 为尚未提交的最终修复生成提交信息并提交。只有本次任务已授权创建 PR 时，才在首次有集成提交后创建草稿，最终验收与审查通过后标记可审查。在本地 spec 与工单文件记录完成状态并交付集成分支；PR 的发布与合并状态单独报告。

7. **清理。** 确认子 agent 的提交已集成，所需资料均留在权威位置，再清理本次创建的 worktree。报告分支、工单状态、构建与数据流测试结果和用户验收记录。
