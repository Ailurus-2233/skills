# Check Result

用于用户已填写验收清单、要求检查结果或继续处理验收问题时。每张 ticket 一次集中验收，修复沿用同一份清单；清单格式与生成要求见 [references/acceptance.md](references/acceptance.md)。

## 1. 读取权威记录

从用户给出的清单或 ticket 路径定位另一份文件，通读 spec、ticket、验收清单（包括问题与历史记录），以及 `.adev/agents/issue-tracker.md`、`verification.md`。只读取主工作区中的权威副本。引用有歧义才询问；缺失清单时按模板补建并交给用户填写，不能据此宣布通过。

核对清单覆盖 ticket 全部验收标准，确认待验版本、实现前基准 SHA、当前工作区及未提交改动范围。版本已变化时判断哪些验收项受影响；没有依据把旧勾选认作新版本结果。

## 2. 判断结果并推进

只把“验收项目”中的用户勾选作为通过证据，问题、历史记录或审查报告中的复选框不能计入。读问题描述而非仅数勾选；空清单、缺少标准、含糊的结果不能通过。

- **有未解决问题或明确失败项**：标记 ticket `in-progress`，在清单的处理记录中列出问题与对应验收项，调用 `implement` 继续实现或修复。信息不足时询问实际现象并保留待处理状态，不能猜测后直接标通过。
- **有未勾选项，但没有失败证据**：保持 `awaiting-verification`，列出待验证项目和执行方法，等待用户填写；不因未勾选就改代码。
- **全部必需项由用户勾选，且没有未解决问题**：在 ticket 追加“用户验收通过”的日期、清单链接和版本记录，进入第 3 步。此时尚不能标记 `done`。

用户勾选和问题原文由用户维护。修复时保留原始反馈及已通过记录，在同一清单追加修复说明；受影响的旧勾选移入历史记录，当前对应项重置为 `[ ]` 并写明原因和复验方法。只让用户复验失败或受影响项，未受影响项保留通过状态。问题是否解决需用户确认或明确撤回；agent 的“已修复”说明不等于用户确认。

## 3. 调用代码审查

调用 `code-review`，提供实现前固化的基准 SHA、ticket、真实 spec、清单路径，以及本次实现和修复的完整差异范围（含相关未跟踪文件）。保留该技能的实现质量与 Spec 两轴，检查仓库代码规范，等待两轴结果。基准或 spec 缺失时补齐来源，不能把未执行审查当作通过。

有审查问题则修复并执行项目构建检查，再以同一基准调用 `code-review` 复核。修复改变可观察行为时，按第 2 步更新同一清单并返回 `awaiting-verification`；用户补验后再次读取结果。纯规范修复经检查确认不影响行为时保留验收结果。未解决审查问题期间 ticket 保持未完成。

## 4. 完成与交付

只有当前版本的用户验收与代码审查均通过，才标记 ticket `done`、解除认领并解锁依赖，记录两类证据链接。沿用 `implement` 的提交约定：调用 `commit-message`，仅提交本 ticket 的实现与修复；由 `implement-spec` 调用时交回主 agent 统一提交与推进依赖。

报告清单路径、判断依据、处理的问题、审查结论和工单状态。重复调用已完成且代码与清单未变化的 ticket 时复用已有证据，不重复追加通过记录或创建空提交；有新问题或新改动则重新判断受影响范围。
