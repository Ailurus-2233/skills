# Ticket 验收清单

每张 ticket 对应 `.adev/<类型>/<yyyy-mm>/<描述>/acceptance/<NN>-<slug>.md`；ticket 中用 `**验收清单：**` 链接它。实现完成且构建及所需数据流测试通过后一次性交付，覆盖全部标准。已有清单原地更新，保留用户勾选、问题与历史；不生成多份结果副本。

清单使用 Markdown 列表，不使用表格。每项有稳定编号、前置条件、具体操作、观察位置和明确通过标准；不能只写“验证正常”。注明实际启动命令/入口、环境、所需数据或设备及日志路径。非 C# 项目按实际验证方式填写。

读取项目验证配置中的自动化测试选择。启用时后台数据流用“数据流自动化测试”记录实际运行证据，由 agent 维护；客户端操作用“手动验收项目”，仅由用户勾选。不启用时后台数据流也写成手动输入输出核对项。无适用项目的分区注明“不适用”及理由；纯后台工单不虚构 UI 步骤。以下为生成模板，交付时替换所有占位内容；条目数量按工单需要确定。

```markdown
# <ticket 标题>：验收清单

- 工单：[<标题>](../issues/<NN>-<slug>.md)
- Spec：[规格](../spec.md)
- 实现前基准：<固化 SHA>
- 待验版本：<分支、提交及未提交变更标识；足以定位实际运行内容>
- 自动化测试：<启用 / 不启用，引用项目验证配置>
- 验证环境：<依赖、配置、数据或设备>
- 启动方法：<命令或具体操作入口>
- 观察位置：<界面、日志路径或设备现象>

## 填写方法

用户执行每项手动操作，达到全部通过标准后将 `[ ]` 改为 `[x]`。未执行或未通过均保持 `[ ]`；发现问题时在“发现的问题”记录项目编号、步骤、预期与实际现象，以及可用日志。修复后确认解决时在该问题下补写确认结果。自动化测试由 agent 记录实际运行结果，不能代勾手动项。

## 数据流自动化测试

- T1：<后台流程及对应工单标准>
  - 测试位置：<本工作共享 test/ 项目路径；明确使用单元测试项目时填写项目路径>
  - 测试审查基线：<修改前可恢复快照、文件与用例清单；首次创建为空基线>
  - 被测工作区：<实际运行所针对的 checkout 绝对路径>
  - 输入与前置条件：<数据、依赖与状态>
  - 执行入口/命令：<可复现的测试入口>
  - 预期输出：<正常、边界或异常输入对应的输出>
  - 实际结果/证据：<实际输出或断言报告、结果文件、通过/失败/未执行>
  - 运行版本与时间：<被测代码版本、共享测试内容版本或摘要、运行时间>
  - 累计回归：<本次用例及此前所有已验收工单的用例范围、命令、报告与通过/失败/未执行结果>

## 手动验收项目

- [ ] A1：<要验证的行为>
  - 前置条件：<状态与数据>
  - 操作：<可逐步执行的动作>
  - 通过标准：<可观察、可判定的结果及必要边界>
  - 实际结果/证据：<由用户填写，可留空>

## 发现的问题

由用户按项追加；没有问题可写“无”。有问题时使用：
- P1（关联 A1）：<复现步骤、预期、实际现象、日志或截图路径>
  - 用户确认：<待确认 / 已解决及验证结果 / 撤回原因>

## 处理记录

由 agent 追加日期、问题编号、修复内容、构建结果和需复验的项目；旧版本通过记录迁入此处时保留原文与版本。
```

“验收通过”要求两类项目合计非空且覆盖全部标准、本次及此前所有已验收工单的数据流测试均有当前版本的实际通过证据、全部手动项由用户勾选、没有未解决问题。未执行、跳过或只有测试代码而无运行结果均不算通过。构建成功或后台测试通过不能代替客户端操作的用户确认。验收通过后由 `check-result` 调用 `code-review`，两者通过才完成工单。
