# 配置内容

这些是生成目标仓库配置时的语义要求；工单管理统一使用本地 Markdown 文件。

## issue-tracker.md

本地文件操作约定：

- 工作目录：`.adev/<类型>/<yyyy-mm>/<描述>/`。类型读取项目分类 ADR：新功能为 `feature`，性能优化为 `performance`，问题修复为 `repair`；其他类型先在 ADR 定义再使用。`yyyy-mm` 是工作首次建立时按用户时区确定的年月，描述是整项工作的稳定名称（原 `<feature>`）；后续工单、跨月继续及修复沿用同一目录。此类型与 triage 标签分开维护。
- 初始化时在项目 ADR 目录创建或更新工作分类 ADR，记录上述映射，并在 issue-tracker.md 写入其实际路径；已有 ADR 按其定义使用，有冲突先处理，不能另立一份矛盾映射。
- **ADR 工作索引**。分类 ADR 的“工作索引”按实际工作目录一项记录：可点击的目录相对链接、spec 或 MAP 等依据链接、当前工作状态、已完成/总工单数（无工单写“不适用”）、阻塞或待办、更新时间。从 ADR 文件所在目录计算相对链接，不写未展开的占位路径。有关联工作的其他 ADR 也链接此工作目录与分类 ADR 的索引，状态只在分类 ADR 汇总。
- 索引状态由权威工单/地图和验收证据汇总：未开始为 `planned`；存在执行、修复、未解决审查问题或阻塞为 `in-progress`（注明阻塞）；所有实现已交付、仅待用户验证为 `awaiting-verification`；全部必需工单 done 且整体检查完成才为 `done`；工作整体被明确拒绝为 `wontfix`。单张工单 done 或决策工单 closed 不能自动将整个工作标 done。无工单的小改动按实际实现、验证与审查证据汇总，不为状态索引补造 spec/工单。
- 建立工作目录时登记索引；发布、认领、验收、修复、完成、拒绝、重开或迁移时，更新权威记录后立即刷新对应索引项。迁移同时修正关联 ADR 的路径。多 agent 由主 agent 写索引；独立会话先重读再只改目标项，保留其他工作记录。读取发现状态不一致时，以权威记录重算并修正，ADR 的状态不是额外的完成授权。

- spec：`.adev/<类型>/<yyyy-mm>/<描述>/spec.md`；实现工单：`.adev/<类型>/<yyyy-mm>/<描述>/issues/<NN>-<slug>.md`，一工单一文件。
- 验收清单：`.adev/<类型>/<yyyy-mm>/<描述>/acceptance/<NN>-<slug>.md`，ticket 用 `**验收清单：**` 链接；agent 维护数据流自动化证据，用户维护手动项勾选与问题，`check-result` 处理结果并调用 `code-review`。
- 读取：读完整正文与追加记录；评论：追加带日期的小节，保留原文。
- 阻塞：`**阻塞于：**` 引用真实编号/标题；全部依赖已完成才就绪。
- 实现状态：`ready-for-agent` → `in-progress` → `awaiting-verification` → `done`。`done` 要求所需数据流测试、手动验收项与审查问题处理完；失败回到实现，不释放依赖。
- 上述 `ready-for-agent` 是规范角色，实际写入使用标签映射值；`in-progress` / `awaiting-verification` / `done` 是实现生命周期状态，不参加分诊映射。
- 分诊状态和分类字符串取自 `triage-labels.md`；实现中的状态不混作分诊角色。
- 地图：`.adev/<类型>/<yyyy-mm>/<描述>/MAP.md`；决策工单：`.adev/<类型>/<yyyy-mm>/<描述>/tickets/<NN>-<slug>.md`。状态 `open` → `claimed` → `closed`，回答落在工单，地图只加摘要与链接。决策工单不套分诊标签。
- 工单入口为本地文件；未分类报告放在 `.adev/inbox/issues/`，归类后移入确定的工作目录并更新引用。扫描显式包含 `.adev/*/*/*/issues/*.md` 和 inbox，不能依赖旧的单层目录通配符。

工单正文、状态与记录只维护在上述文件中；代码 PR 的创建、审查和合并是独立操作，不作为工单管理的前提。

## triage-labels.md

生成 canonical role → 实际字符串映射，默认一一同名：

| 角色 | 默认字符串 | 含义 |
| --- | --- | --- |
| needs-triage | needs-triage | 待维护者评估 |
| needs-info | needs-info | 待补充信息 |
| ready-for-agent | ready-for-agent | 规格充分，可开始实现，仍需完成适用的测试与手动验收 |
| ready-for-human | ready-for-human | 实现本身需要人完成 |
| wontfix | wontfix | 不处理 |
| bug | bug | 缺陷分类 |
| enhancement | enhancement | 新功能或改进分类 |

## verification.md

按事实记录项目类型、构建命令、启动方式、日志与观察入口、仿真或真机要求，并保存以下验证约定：

- **自动化测试：启用 / 不启用**，取用户的明确选择；缺少选择时请用户补充，不能自行套用默认值。后续 skill 读取此选择，启用后不必逐工单再次征求测试授权。
- **启用范围：后台数据流**。测试以输入数据、执行入口、预期输出为标准，覆盖相关正常、边界和异常数据；仅验证后台流程的输入输出正确性。记录运行命令、环境依赖和结果位置；尚无入口时写明由相关实现工单建立。
- **共享测试项目**。同一工作目录内所有工单共用 `.adev/<类型>/<yyyy-mm>/<描述>/test/` 中的一个测试项目，逐工单向该项目增加用例，不再按工单创建测试项目。测试脚本、数据和运行产物也归入该目录；用例标注来源工单，运行报告按版本与执行批次区分。此前明确构造在单元测试项目中的测试仍可沿用该项目，记录实际路径并纳入累计回归，不因仓库已有测试项目就自行采用例外。工单与验收清单记录共享项目路径、执行命令、实际被测工作区及测试内容版本；共享目录随 `.adev/` 保持本地。
- **累计回归**。每张工单交付、修复和批次集成时，运行本次新增用例与此前所有已验收工单的测试，明确使用当前被测代码和共享测试内容。旧用例失败或未执行均不能验收本工单、标记 done 或解锁依赖；不得通过删除、跳过或弱化旧断言制造通过。需求确需改变已验收行为时，先取得用户确认并更新 spec 与受影响的验收标准，保留变更记录，再调整用例并重新验收。
- **共享写入与运行**。多 worktree 只使用主工作区中这一共享项目；由主 agent 统一写入和执行，子 agent 提供测试变更草稿。主 agent 针对已集成代码串行运行，避免并发修改项目或覆盖构建产物；不能将子分支测试结果当成集成回归证据。
- **测试审查基线**。修改共享项目之前，为当前工单/集成批次保存可恢复的只读快照和文件、用例清单；首次创建记录空基线。每次验收保留对应快照与报告，修复沿用原实现基线。存入 test/ 内独立证据目录，并排除编译与测试发现；不能仅保存不可恢复的摘要。审查显式比较基线与当前测试源码、配置、数据及用例清单，即使它们被 Git 忽略。已有项目缺失基线时保留现状并报告无法核对历史变化的边界，不能宣称旧断言未变。
- **客户端操作：用户手动验收**。界面点击、导航、编辑及完整操作流程由用户实际执行并确认，不能由 UI 自动化或后台测试通过代替。
- 不启用时不新增自动化测试，后台数据流也提供可手动执行的输入与输出核对步骤。已有检查按项目要求运行，不把运行已有检查视为修改用户选择。

每张 ticket 全部实现且构建及累计数据流回归通过后一次集中验收，生成独立 Markdown 列表清单，格式按 `check-result/references/acceptance.md`。清单分别记录数据流测试的命令、输入、预期与实际输出、代码与测试内容版本及累计回归结果，以及用户填写的手动验收项与问题；`check-result` 检查两类证据，通过后调用 `code-review`。纯后台工单启用自动化时可以只含数据流测试项，不虚构客户端操作。修复沿用原清单，重跑累计回归，只让用户复验受影响手动项；编译成功不等于验收通过。没有对应工具或设备时如实记录阻塞。

## domain.md

记录单/多上下文路径及分类 ADR 的实际路径。关联具体工作的 ADR 链接工作目录及分类 ADR 的状态索引，按 issue-tracker.md 的汇总规则维护，区别于 ADR 决策状态。探索前读 `.adev/GLOSSARY.md`，或从 `.adev/GLOSSARY-MAP.md` 选择相关词汇表，再读触及区域的 ADR。文件不存在则继续，不预建空文档；已存在时使用规范术语，冲突须说明。词汇表只记录领域概念，ADR 默认标题 + 1–3 句背景、决定、理由，复杂决策按需展开。
