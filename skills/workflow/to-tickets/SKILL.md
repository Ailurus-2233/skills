# To Tickets

把计划、spec 或对话拆成一组**工单**：tracer-bullet 式的纵向切片，每个声明哪些工单**阻塞**它。

工单跟踪方式和 `.adev/agents/triage-labels.md` 标签映射应当已由 `/setup-dev-workflow` 配置好。缺少工单或验证配置时提示用户先运行 `/setup-dev-workflow`。若未安装 triage、初始化因此未生成标签映射，则沿用规范角色名，不为缺少这份可选文件阻塞。

## 流程

### 1. 收集上下文

利用对话中已有的内容。用户传了引用（spec 路径、工单号）作为参数时，取回并通读全文与评论。若输入只有计划或对话、尚无持久化 spec，发布前请用户指定真实 spec 或通过 `/to-spec` 保存，再在工单中引用。

### 2. 探索代码库（可选）

还没探索过则探索。工单标题和描述使用项目领域词汇，尊重所触及区域的 ADR。

留意**预重构**机会：让后续实现变容易的先行改动。"先让改动变容易，再做容易的改动。"

### 3. 草拟纵向切片

把工作拆成 **tracer bullet** 工单：

- 每个切片切出一条**窄而完整**的通路，穿过各层（通信层 → 业务逻辑 → UI）：是纵向切片，不是某一层的横切
- 完成的切片**可独立手动验证**：用户能启动程序、操作界面、观察到这条通路的行为
- 每个切片大小以**一个全新上下文窗口能装下**为准
- 预重构排在最前

给每个工单声明**阻塞边**：必须先完成的其他工单。无阻塞的工单可立即开始。

**宽重构是纵向切片的例外。** 一次机械改动（改公共协议结构、重命名共享类型）波及全代码库、任何纵向切片都无法独立落地时，按 **expand–contract** 排：先扩展（新旧并存、不破坏任何调用点），再分批迁移（每批一个工单、保持可编译），最后收缩（删除旧形式）。每张交付验收的 ticket 必须可编译；若迁移批次仍不能独立编译，合并工单并重新与用户核对粒度，不采用直到最终集成才保证编译通过的方案。

### 4. 与用户核对

以编号列表展示拆分方案。每个工单给出：

- **标题**：简短描述
- **阻塞于**：哪些工单必须先完成
- **交付什么**：这个工单让哪条端到端行为可用、用户怎么验证

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边对吗？每个工单只依赖真正卡住它的工单吗？
- 有该合并或该再拆的吗？

迭代到用户认可。

### 5. 发布工单

按 `.adev/agents/issue-tracker.md` 的本地文件约定发布：

在 `.adev/<feature-slug>/issues/` 下每工单一个文件，命名 `<NN>-<slug>.md`，从 `01` 起按依赖顺序编号（阻塞者在前）。用下面的本地模板，状态填入配置映射的实际字符串：一工单一个文件，绝不合并成一个文件。

按 **frontier** 推进：所有阻塞项都完成的工单就能开工。纯线性链就是从头做到尾。

保留真实 spec 的文件路径，写入每张工单，供实现与审查读取。`ready-for-agent` 表示可开始实现；工单只有全部手动验收且代码审查通过才完成，依赖才解锁。不要关闭或修改任何父工单。

<local-ticket-template>

# <NN>：<工单标题>

**要构建什么：** 这个工单让哪条端到端行为可用，从用户视角描述，不是逐层的实现清单。

**阻塞于：** 阻塞它的工单编号/标题，或 "无（可立即开始）"。

**状态：** <triage-labels.md 中 ready-for-agent 对应的实际字符串>

**Spec：** <真实 spec 的文件路径>

## 验收标准（实现后生成独立清单）

- 步骤 1：启动/操作/明确通过标准
- 步骤 2：……

</local-ticket-template>

验收标准必须写成**用户可执行的手动验证步骤**：写什么动作、看什么界面/日志/设备现象、预期结果是什么。不要写成自动化测试的断言。工单只定义标准；`implement` 完成整张 ticket 后按 `check-result/references/acceptance.md` 生成独立验收清单并写入链接，用户只在该清单勾选结果，避免维护两套勾选状态。

避免具体实现文件路径和代码片段，它们很快过时；真实 spec 等上下文指针仍须保留。例外同 to-spec：决策密度高的小片段可以内联并注明来源。
