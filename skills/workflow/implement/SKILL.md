# Implement

实现用户指定的 spec 或工单。读取 `.adev/agents/verification.md` 中用户的自动化测试选择；启用时实现并运行后台数据流输入输出测试，不启用时提供手动核对步骤。选择缺失时请用户补充并保存；客户端操作始终由用户手动验收。C# 桌面端使用实际项目的 dotnet build 或等价构建入口，其他项目遵循其验证配置。

## 流程

按验证配置在首次修改测试前保存共享测试的可恢复基线与用例清单；修复沿用原基线。登记或刷新分类 ADR 的工作目录索引，在认领、交付、修复后按工单记录重算工作状态；不要将单工单状态直接赋给整项工作。

创建自动化测试前读取验证配置：同一工作目录的所有工单共用 `.adev/<类型>/<yyyy-mm>/<描述>/test/` 中的一个项目，在其中追加用例；此前明确构造在单元测试项目中的测试按配置沿用并纳入回归。旧配置仍按工单建测试项目时，按 setup-devenv 迁移到共享项目。每次交付和修复均执行本次用例及此前所有已验收工单的累计回归，旧用例失败或未执行时继续处理，不能交付通过；不能删除、跳过或弱化旧断言规避失败。测试命令明确指向实际被测工作区，清单保留代码版本、共享测试内容版本及累计回归证据。

1. **明确来源。** 按 `.adev/agents/issue-tracker.md` 读取本地 ticket、关联 spec 和追加记录，确认阻塞项均已完成。记录实现前固化的 Git 基准 SHA、分支和已有无关改动，供后续累计审查；继续修复时保留原基准。缺少真实 spec 或引用不明确时请用户指定，不以会话记忆代替。直接实现 spec 时，以本次完整实现范围作为一张 ticket，在本地保存对应工单。
2. **实现整张 ticket。** 标记 `in-progress`，可在内部拆分可编译片段并采用 expand–contract，但不逐片段请求用户验收。完成全部标准并执行项目构建检查及所需数据流测试；遇到需求冲突或缺失的外部条件时说明具体阻塞。
3. **生成验收清单。** 读取 [清单约定与模板](../check-result/references/acceptance.md)，创建 `.adev/<类型>/<yyyy-mm>/<描述>/acceptance/<NN>-<slug>.md`，在 ticket 写入清单链接与原始审查基准。根据真实实现填齐环境、启动方法、操作与通过标准。清单覆盖 ticket 全部标准，使用列表而非表格。修复任务沿用原清单，保留用户反馈；只更新受影响项及复验方法，不替用户勾选。
4. **一次性交付验收。** 构建及所需数据流测试通过后标记 `awaiting-verification`，报告实现结果、构建与测试证据和清单的可点击路径。说明用户勾选手动项、记录问题后使用 `/check-result <清单路径>`。有手动项时等待用户填写；纯后台且全部标准已有自动化证据时直接调用 check-result。不逐片段等待口头确认，不提前完成工单或解锁依赖。

用户提交结果后由 `check-result` 判断待验证、继续修复或验收通过，并调用 `code-review` 完成审查与收尾。修复仍属于同一张 ticket 的同一次集中验收流程，不重新要求验证未受影响的已通过项目。
