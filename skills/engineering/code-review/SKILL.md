name: code-review
description: "审查某个固定点（commit、分支、tag、merge-base）以来的仓库变更，沿两条轴进行：实现质量（实现方式是否合理、是否符合 SOLID、有无风险、注释是否得当）和 Spec（实现是否符合工单/spec 的要求）。两轴用并行子 agent 审查后并列汇报。当用户想审查一个分支、一批未提交改动，或说 \"review 一下 X 以来的改动\" 时使用。"
---

对 `HEAD` 与用户指定的固定点之间的 diff 做两轴审查：

- **实现质量**：代码实现方式是否合理、是否遵守 SOLID、有无风险、注释是否得当
- **Spec**：代码是否忠实实现了来源工单 / spec 的要求

两轴各用一个**并行子 agent** 执行，避免互相污染上下文，最后由本 skill 汇总。

工单跟踪约定应已由 `/setup-dev-workflow` 配置（`.adev/agents/issue-tracker.md`）。缺失时提示用户先运行它。

## 流程

### 1. 锁定固定点

用户指定什么就是什么（SHA、分支名、tag、`main`、`HEAD~5` 等）。

先将固定点解析为 SHA，记录起始提交列表。用户未指定、且明确审查当前未提交改动时，固定点才默认 `HEAD`；其余情况询问。调用者已传入实现前基准时始终保留它。

- 仅审查已提交分支：记录 `git merge-base <fixed-point> HEAD` 的结果，用该 SHA 到 `HEAD` 的 diff（等价于三点比较）。
- 审查包含未提交的实现/修复：从同一个已固化的基准 SHA 到当前工作区做 `git diff <base-sha>`，覆盖已提交、暂存与未暂存的累计变化；不要改成仅 `git diff HEAD` 而漏掉原有实现。
- 用 `git ls-files --others --exclude-standard` 列出新文件，识别本次任务的文件并逐个读取；它们不出现在普通 diff 中。保留并标明任务开始前已有的无关改动。

确认审查集合非空：已跟踪 diff 与本次新文件取并集，两者都为空才是无改动。把固化基准、准确命令、提交列表和新增文件清单传给两轴；复核修复时仍用相同基准。坏引用或空审查集合在此报告，不派子 agent 空跑。

### 2. 定位 spec 来源

先使用用户明确指定的 spec / 工单；否则依次检查提交消息中的引用（按 `.adev/agents/issue-tracker.md` 取回）、用户参数中的路径、与分支或功能对应的 `.adev/` / `specs/` / 项目文档中的 spec。已有会话中的文件引用可以帮助定位，但会话需求本身不是 spec。

取回正文和相关评论，把具体路径或真实 tracker 引用及完整内容提供给 Spec 子 agent，并记录报告落点。找不到时询问用户 spec 在哪里；只有用户明确表示不存在，才跳过 Spec 轴并报告“无 spec 可对照”。等待回答期间可独立完成实现质量轴，不把缺少 spec 当作审查通过。

### 3. 定位规范来源

搜索仓库中所有记录代码写法的文档，列出实际找到的规范路径。`CODING_STANDARDS.md`、`CONTRIBUTING.md` 存在时必须纳入；另查 AGENTS 指向的文档和 `.adev/agents/`。`.adev/` 被忽略时需要显式读取，不能把默认搜索未返回当作不存在。

在仓库文档之上，实现质量轴始终携带以下**基线**。两条约束：

- **仓库约定优先。** 仓库成文的规范总是赢；它认可的做法即使触发基线也不报。
- **基线永远是判断题。** 每项是带标签的启发式（"疑似 Feature Envy"），不是硬性违规；工具（编译器警告、Roslyn 分析器、IDE 规则）已强制的一律跳过。

**坏味道（Fowler _Refactoring_ ch.3，按 diff 匹配）**：Mysterious Name、Duplicated Code、Feature Envy、Data Clumps、Primitive Obsession、Repeated Switches、Shotgun Surgery、Divergent Change、Speculative Generality、Message Chains、Middle Man、Refused Bequest。每条按"是什么 → 怎么改"对照 diff 中的 hunk。

**SOLID**（针对 C# 桌面端的具体化）：

- **SRP**：一个类是否同时承担 UI 事件、业务规则、设备通信中的多项职责
- **OCP**：新增设备型号/协议是否要改既有 switch/if 级联，而不是扩展
- **LSP**：子类/实现是否忽略了基类契约（对应 Refused Bequest）
- **ISP**：接口是否臃肿，强迫实现方实现用不到的方法
- **DIP**：业务逻辑是否直接 new 具体通信类/硬件访问类，而不是依赖抽象

**风险**：

- 线程与并发：UI 线程阻塞、跨线程访问控件、未保护的共享状态、`async void`、吞掉的 `Task`
- 资源与句柄：串口/Socket/订阅未释放，`IDisposable` 未实现或未使用 `using`
- 异常吞噬：空 `catch`、`catch` 后静默继续、异常导致设备状态不一致
- 工控特有：超时与重连逻辑缺失、报文解析无边界检查、设备断连后状态未复位

**注释**：

- **缺失**：非显然的逻辑（协议字节偏移、时序要求、硬件怪癖 workaround）没有注释说明**为什么**
- **过于复杂/冗余**：注释复述代码本身（`i++ // 自增`）、大段注释掉的死代码、注释与代码已不一致、XML 文档注释只是复读成员名

### 4. 并行派两个子 agent

同轮启动两轴审查并等待全部结果后汇总，不把后台尚未返回当作无问题。

**实现质量子 agent** 的输入：

- diff 命令、提交列表和本次新增未跟踪文件的路径清单（逐个读取完整内容）
- 第 3 步找到的规范文件清单，**加上完整粘贴的基线内容**（子 agent 没有其他途径获得它）
- 任务说明："按文件/hunk 报告：(a) 违反仓库成文规范之处，引用规范（文件+规则）；(b) 发现的基线条目，命名并引用 hunk。硬性违规与判断题分开：成文规范的违反可以是硬性的，基线条目永远是判断题，仓库成文规范覆盖基线。工具已强制的跳过。400 字以内。"

**Spec 子 agent** 的输入：

- diff 命令、提交列表和本次新增未跟踪文件的路径清单（逐个读取完整内容）
- spec / 工单的路径或取回的完整内容
- 任务说明："报告：(a) spec 要求但缺失或部分实现的需求；(b) diff 中没人要求的行为（范围蔓延）；(c) 看似实现但实现方向有误的需求。每条引用 spec 原文。400 字以内。"

无 spec 时跳过 Spec 子 agent，并在最终报告中注明。

### 5. 汇总与落点

在 `## 实现质量` 和 `## Spec` 两个标题下原样（或轻度整理）并列呈现两份报告。**不要**合并或跨轴排序——两轴刻意分离：代码可以完全符合规范但做错了事，也可以做对了事但破坏约定，分开呈现防止一轴掩盖另一轴。

结尾一行总结：每轴的发现数和**各自轴内**最严重的问题（如有）。

**输出落点**：

- 第 2 步找到了工单 → 把完整审查报告**追加到该工单文档**（本地 markdown 工单：在文件末尾加 `## Code Review 报告（<日期>）` 一节；真实 tracker：有发布评论授权时发表，否则把待发布报告交给用户）。报告中存在的问题项前标 `[ ]`，方便修复后勾选。
- 没有工单 → 直接把汇总输出到当前会话，方便用户（和 agent）接着修改，不写入任何文件。
