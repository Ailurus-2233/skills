# 改进代码库架构

暴露架构上的摩擦，提出**加深机会**：把浅模块变成深模块的重构。目标是可验证性与 agent 可导航性。

本命令以项目的领域模型为*依据*，并建立在一套共享的设计词汇之上：

- 调用 Skill 工具的 "codebase-design"，获取架构词汇（**模块**、**接口**、**深度**、**缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口就是验证面"、"一个适配器 = 假想的缝，两个 = 真实的缝"）。每条建议都要严格使用这些术语，不要滑向"组件""服务""API""边界"。
- `CONTEXT.md` 里的领域语言给好的缝命名；`docs/adr/` 里的 ADR 记录着本命令不应重新翻炒的决策。

## 流程

### 1. 探索

**先定范围再扫描：YAGNI。** 加深一个模块的回报在于让未来对它的改动更容易，所以要多给最近改动过的部分加权。先看哪里，再决定看什么：

- 用户给了方向（某个模块、某个子系统、某个痛点）就照着走，跳过下面的推断。
- 否则，回看足够长的一段提交历史（`git log --oneline`），找出代码库的热点——反复出现的文件和区域，让这些路径先拉住你的注意力。改动分散、没有明显热点时，再把网撒大。

先读项目的领域词汇表（`CONTEXT.md`）和你所触及区域的 ADR。

然后派出一个子 agent 走查代码库。不要套死板的启发式；有机地探索，记下你体验到摩擦的地方：

- 哪里要理解一个概念，得在一大堆小模块之间来回跳？
- 哪些模块是**浅**的，接口几乎和实现一样复杂？
- 哪里把纯函数抽出来只是为了"好测"，而真正的缺陷藏在它们的调用方式里（没有**局部性**）？
- 哪些紧耦合的模块在缝上互相渗漏？
- 哪些部分无法通过接口手动验证，或 agent 难以顺着接口导航？

对任何疑似浅模块的东西做**删除测试**：删掉它会让复杂度集中，还是只是挪了个地方？"会集中"正是你要找的信号。

### 2. 以 HTML 报告呈现候选项

写一个自包含的 HTML 文件到系统临时目录，不往仓库里落任何东西。写到 `%TEMP%\architecture-review-<时间戳>.html`，每次运行一个新文件。用 `start <路径>` 为用户打开，并告知绝对路径。

报告用 **Tailwind CDN** 做布局样式，**Mermaid CDN** 画图；Mermaid 画关系成图的东西（调用图、依赖、时序），手工 div/内联 SVG 画更编辑化的东西（体量图、剖面图、调用树坍缩）。两者混用，别全靠 Mermaid，否则看起来千篇一律。每个候选项配一张**前后对比图**。要视觉化。

骨架如下，图例与配色约定照用：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="utf-8" />
    <title>{{仓库名}} 架构评审</title>
    <script src="https://cdn.tailwindcss.com"></script>
    <script type="module">
      import mermaid from "https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs";
      mermaid.initialize({ startOnLoad: true, theme: "neutral", securityLevel: "loose" });
    </script>
    <style>
      /* Tailwind 覆盖不干净的小东西：虚线缝、手绘感箭头 */
      .seam { stroke-dasharray: 4 4; }
      .leak { stroke: #dc2626; }
      .deep { background: linear-gradient(135deg, #0f172a, #1e293b); }
    </style>
  </head>
  <body class="bg-stone-50 text-slate-900 font-sans">
    <main class="max-w-5xl mx-auto px-6 py-12 space-y-12">
      <header>...</header>
      <section id="candidates" class="space-y-10">...</section>
      <section id="top-recommendation">...</section>
    </main>
  </body>
</html>
```

页头只放仓库名、日期和一行紧凑图例：实心框 = 模块，虚线 = 缝，红箭头 = 渗漏，粗黑框 = 深模块。不写引言段，直接进候选项。

每个候选项渲染一张卡片（一个 `<article>`），图承重，文字稀疏：

- **标题**：短，点出这次加深（如"收拢工单接收管线"）。
- **徽章行**：推荐力度 `Strong`（翠绿）/ `Worth exploring`（琥珀）/ `Speculative`（石灰），再加一个依赖类别标签（`进程内` / `本地可替换` / `端口与适配器` / `占位`）。
- **文件**：等宽列表，`font-mono text-sm`。
- **前后对比图**：卡片的主角。两列并排。按候选项挑图式并换着用：Mermaid 流程图（依赖/调用流，渗漏边染红、深模块染深色；时序图适合"前：6 次往返；后：1 次"）、手工盒子加箭头（after 想画成一个粗边框深模块、内部灰掉时）、剖面图（横向色带堆叠，前：6 条薄带各自空转，后：1 条粗带标上收拢后的职责）、体量图（每个模块两个矩形：接口面积与实现面积，前：两者几乎等高 = 浅；后：接口矮、实现高 = 深）、调用树坍缩（前：嵌套盒子的调用树；后：坍缩成一个盒子，已内部化的调用淡显其中）。图高约 320px，并排不用滚动。
- **问题**：一句话。痛在哪。
- **方案**：一句话。改什么。
- **收益**：bullet，每条 ≤6 个字，用词汇表术语命名所得："局部性：缺陷聚在一处"、"杠杆：一个接口，N 个调用点"、"接口收窄，实现吞掉转发"。不写"更易维护""代码更干净"——这些词不在词汇表里，不配出现。
- **ADR 提示**（如适用）：琥珀色底框里一行字。

**领域用 `CONTEXT.md` 的词汇，架构用 `/codebase-design` 的词汇。** 如果 `CONTEXT.md` 定义了"工单"，就说"工单接收模块"，不说"GongDanHandler"，也不说"工单服务"。

**ADR 冲突**：候选项与既有 ADR 矛盾时，只在摩擦真实到值得重开该 ADR 时才摆出来，并在卡片上标清楚（如琥珀色警示框：_"与 ADR-0007 冲突，但值得重开，因为……"_）。不要把 ADR 禁止的每一个理论上的重构都列一遍。

风格：编辑感，不是企业仪表盘。留白大方；颜色克制——一个主色（翠绿或靛蓝），红色只给渗漏，琥珀只给警示；图内模块标签用 `text-xs uppercase tracking-wider`，读上去像示意图而不是 UI；除 Tailwind CDN 与 Mermaid ESM 外无脚本。

报告以 **Top recommendation** 一节收尾：一张更大的卡片，你会先动哪个候选项、为什么，附一个跳到该卡片的锚链接。

此阶段**不要提接口设计**。文件写完后问用户："想先探索哪一个？"

### 3. 追问（grilling）循环

用户挑定候选项后，调用 Skill 工具的 "grilling"，陪他走决策树：约束、依赖、加深后模块的形状、缝后面放什么、哪些手动验证步骤仍然有效。

副作用随决策定型就地发生；调用 Skill 工具的 "domain-modeling"，随时保持领域模型为最新：

- **用 `CONTEXT.md` 里没有的概念给加深后的模块命名？** 把该术语补进 `CONTEXT.md`。文件不存在就懒惰创建。
- **对话中敲细了一个模糊术语？** 当场更新 `CONTEXT.md`。
- **用户带着承重理由否决了候选项？** 提供一份 ADR，措辞如：_"要不要我把这个记成 ADR，免得以后的架构评审再提同样的建议？"_ 只在该理由确实是未来探索者避免重蹈所需时才提供； 转瞬即逝的理由（"眼下不值得"）和不说自明的理由跳过。
- **想为加深后的模块探索备选接口？** 调用 Skill 工具的 "codebase-design"，用其"设计两次"的并行子 agent 模式。
