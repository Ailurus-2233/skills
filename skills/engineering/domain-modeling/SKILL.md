# 领域建模

在设计过程中主动构建并打磨项目的领域模型。这是*主动*的纪律：质疑术语、编造边界场景、在术语与决策定型的一刻就把它们写下来。（仅仅*读* `CONTEXT.md` 查词汇不算本 skill：那是任何 skill 都该有的顺手习惯。本 skill 管的是你在改动模型，而不只是在消费它。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明仓库有多个上下文。地图指向每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文自己的决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

懒惰创建文件：只在有东西可写时才创建。没有 `CONTEXT.md`，就在第一个术语敲定时创建它；没有 `docs/adr/`，就在第一份 ADR 需要落笔时创建它。

## 会话进行中

### 对照词汇表质疑

用户用的词与 `CONTEXT.md` 里的既有语言冲突时，立刻指出："你的词汇表把'取消'定义为 X，但你刚才的意思似乎是 Y。到底是哪个？"

### 打磨模糊语言

用户用词含糊或一词多义时，提出一个精确的规范术语："你说'账户'，指的是客户还是用户？这是两个东西。"

### 讨论具体场景

讨论领域关系时，用具体场景做压力测试。编造能探到边界的场景，逼用户把概念之间的界线说精确。

### 与代码交叉核对

用户陈述某物如何工作时，检查代码是否一致。发现矛盾就摆出来："你的代码会取消整张工单，但你刚才说可以部分取消。哪个是对的？"

### 就地更新 CONTEXT.md

术语一敲定，当场更新 `CONTEXT.md`。不要攒批：随发生随记录。格式如下：

```markdown
**术语**：定义（一两句话，只讲领域含义）。

_避免_：同义误用词（说明它常被错当成这个术语）。
```

`CONTEXT.md` 必须完全不含实现细节。不要把它当规格书、草稿纸或实现决策的仓库。它只是词汇表，别无他物。

### 克制地提供 ADR

只在以下三条全部成立时，才提议创建 ADR：

1. **难以逆转**：日后改主意的代价是实打实的
2. **缺了上下文会让人费解**：未来的读者会纳闷"他们当时为什么这么做？"
3. **真实权衡的结果**：确实存在过像样的备选方案，而你因为具体理由选了其中一个

三条缺任何一条，就跳过 ADR。格式如下：

```markdown
# 标题（名词短语，如"工单写入模型用 SQL Server"）

## 状态
已接受 / 已废弃 / 已被 ADR-XXXX 取代

## 上下文
迫使做这个决策的事实与约束。

## 决策
我们决定做什么。

## 后果
这个决策带来的好处与代价，包括被否掉的备选及其理由。
```
