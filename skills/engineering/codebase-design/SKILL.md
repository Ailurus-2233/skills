# 代码库设计

设计**深模块**：小接口背后承载大量行为，安放在干净的缝上，可以通过该接口验证。凡是在设计或重构代码的地方，都用这套语言和这些原则。目标：给调用方以杠杆，给维护者以局部性，给所有人以可验证性。

## 词汇表

严格使用这些术语：不要替换成"组件""服务""API""边界"。语言一致本身就是目的。

**模块**：任何有接口和实现的东西。刻意与规模无关：可以是一个函数、一个类、一个程序集，或一条跨层切片。_避免_：单元、组件、服务。

**接口**：调用方要正确使用模块必须知道的一切：类型签名，还有不变量、时序约束、错误模式、必需的配置、性能特征。_避免_：API、签名（太窄，它们只指类型层面的表面）。

**实现**：模块内部的代码本体。与**适配器**区分开：一个东西可以是小适配器大实现（对接真实 PLC 的通讯通道），也可以是大适配器小实现（内存仿真件）。话题在缝上时用"适配器"，否则用"实现"。

**深度**：接口处的杠杆。调用方（或验证者）每学习一单位接口，能驱动多少行为。大量行为藏在小接口后面，模块就是**深**的；接口的复杂度逼近实现的复杂度，就是**浅**的。

**缝**（Michael Feathers）：不改这个位置就能改变行为的地方；模块接口所在的*位置*。缝放哪里本身是一个设计决策，与缝后面放什么是两回事。_避免_：边界（与 DDD 的限界上下文撞车）。

**适配器**：在缝上满足接口的具体东西。描述的是*角色*（填哪个槽位），不是*内容*（里面装了什么）。

**杠杆**：调用方从深度中得到的东西。每学一单位接口换来更多能力。一个实现回报 N 个调用点和 M 条验证路径。

**局部性**：维护者从深度中得到的东西。变更、缺陷、知识、验证集中在一处，而不是摊到各个调用方。修一次，处处修好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口         │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│      深的实现        │  ← 复杂逻辑被藏起来
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 很少实现（要避免）：

```
┌─────────────────────────────────┐
│            大接口                │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  薄薄的实现                      │  ← 只是转发
└─────────────────────────────────┘
```

设计接口时自问：

- 方法数能不能再减？
- 参数能不能再简化？
- 还能把多少复杂度藏进去？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可替换的部件组合而成，只要它们不属于接口。模块除了有位于接口处的**外部缝**，还可以有**内部缝**（实现私有，供模块自身的验证使用）。
- **删除测试。** 想象把这个模块删掉。如果复杂度随之消失，它本来就是个转发器；如果复杂度在 N 个调用方身上重新冒出来，它就是在挣钱。
- **接口就是验证面。** 调用方与验证跨过同一条缝。想越过接口去验证内部，多半是模块的形状错了。本仓库不写自动化测试：所谓"通过接口验证"，指启动程序、在界面上操作、观察现象的手动验收，以及 agent 顺着接口导航代码。
- **一个适配器是假想的缝，两个适配器才是真实的缝。** 没有东西真的在缝上变化，就不要引入缝。

## 为可验证性设计

好接口让验证自然发生：

1. **接受依赖，而不是创建依赖。**

   ```csharp
   // 可验证：通道可以换成仿真器，界面操作即可走通
   public void Settle(WorkOrder order, IPlcChannel channel) { ... }

   // 难验证：写死真实设备，没有 PLC 就寸步难行
   public void Settle(WorkOrder order) {
       var channel = new SiemensS7Channel("192.168.0.10");
   }
   ```

2. **返回结果，而不是制造副作用。**

   ```csharp
   // 可验证：看返回值即可断言结果
   public Discount CalculateDiscount(Cart cart) { ... }

   // 难验证：必须检查对象被改动了什么
   public void ApplyDiscount(Cart cart) {
       cart.Total -= discount;
   }
   ```

3. **小表面。** 方法越少，要验证的路径越少；参数越少，验证的准备工作越简单。

## 关系

- 一个**模块**恰有一个**接口**（它呈现给调用方和验证的表面）。
- **深度**是**模块**的属性，对着它的**接口**度量。
- **缝**是**模块**的**接口**所在的位置。
- **适配器**坐在**缝**上，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被拒绝的表述

- **深度 = 实现行数 / 接口行数**（Ousterhout）：奖励往实现里灌水。我们用"深度 = 杠杆"。
- **把"接口"当成 C# 的 `interface` 关键字或类的公开方法**：太窄。这里的接口包括调用方必须知道的每一个事实。
- **"边界"**：与 DDD 的限界上下文撞车。说**缝**或**接口**。

## 再深一步

- **带着依赖加深一簇模块**：先把依赖分类——进程内调用、本地可替换的（文件、时钟、随机数）、需要端口与适配器的外部系统（PLC、串口、总线、数据库）、以及纯属占位的东西——再守缝的纪律：缝划在哪一类依赖上，替换就发生在哪一类上。验证走"替换适配器"（真机换仿真器），而不是在调用栈上再包一层；叠层只会把缝推远。
- **探索备选接口（设计两次）**：并行派出多个子 agent，各自把同一个模块的接口设计成差异悬殊的两版（例如一版以命令为中心、一版以查询/事件流为中心），再按深度、局部性、缝的位置逐一比较，挑出最经得起删除测试的那版，而不是把第一版直接落地。
