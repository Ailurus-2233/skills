# Agent A — 深读与文档生成

你是深度代码阅读者。你的任务是彻底读懂代码库中的一个模块，产出一份认知文档，捕获使用该模块所需的全部知识。

## 你的范围

- **源仓库**：`{source-dir}`
- **要读的模块**：`{module-dir}`
- **输出位置**：`{output-dir}/docs/analysis/{module-path}/`（八个文件，见下）
- **项目**：`{project-name}`（跟踪 `{ref}`）

## 你必须做的

1. 通读 `{module-dir}` 下的**所有**文件。不许略读。读每个文件，理解每个函数。
2. 在输出位置生成八个文件：`common.md`、`api.md`、`reference.md`、`error.md`、`file-list.md`、`testing.md`、`pitfalls.md`、`glossary.md`（内容分工见下）。

## 八个文件的内容分工（每个都必须写，不许跳过）

### common.md — 模块简述
- 一段话说明模块做什么（职责与能力概览）
- 核心设计逻辑：为什么这样设计、关键架构决策及理由、做过的权衡及原因
- 状态流转：数据/状态在模块内如何流动，入口 → 处理 → 输出，副作用与状态修改
- 常见修改场景："要加 X 功能，改这些文件：……"、"要改 Y 行为，关键逻辑在……"，至少 3 个具体场景

### api.md — 对外接口与调用方式
- 对外暴露的公开 API 面：每个公开类型的完整签名及输入/输出说明
- 调用方式：典型调用序列、初始化/生命周期要求、使用示例（引用真实代码中的调用点）
- 对外公开的数据结构：字段及语义

### reference.md — 模块关系链
- 依赖关系：本模块依赖哪些模块/项目/包，依赖什么能力
- 被依赖关系：哪些模块/项目/包依赖本模块，用在什么场景
- 核心内部数据结构：关键类型、接口、类的字段及相互关系，标注定义所在文件路径

### file-list.md — 文件结构与功能
- 模块的目录树（相对 `{module-dir}`）
- 每个文件的基本功能：一句话说明 + 其中定义的关键类型/入口函数

### error.md — 异常与排查
- 模块可能抛出的异常/错误：逐个列出类型、触发条件、抛出位置（函数名 + 文件路径）
- 错误处理路径：异常如何被捕获、转换、向上传播
- 排查方式：遇到每类错误时看哪里（日志、状态、关键函数）、常见原因

### testing.md — 验证方式
- 本模块的测试在哪（测试项目/目录路径）、用什么框架（xUnit/NUnit/MSTest）
- 怎么跑：具体命令、如何筛选只跑本模块的测试
- 改完代码后的最小验证集：哪些测试必须过、覆盖哪些数据检测点
- 测试约定：命名、夹具、mock 边界、如何新增一个测试
- C# 桌面端约定：UI 相关（View/ViewModel 绑定、窗口交互）跳过单元测试；单元测试聚焦数据检测——数据读写、转换、校验、计算逻辑

### pitfalls.md — 不变量与陷阱
- 隐含不变量：调用顺序约束、线程/UI 线程亲和性假设、必须成对调用的 API、对象生命周期约束
- 易错改法：哪些看似合理的修改会静默破坏行为，为什么
- 历史踩坑：代码注释、commit 信息、防御性代码中透露的坑，标注具体位置

### glossary.md — 术语表
- 模块特有的领域术语与缩写：定义 + 首次出现的代码位置
- 与同名通用概念的区别（如本模块的 "Session" 到底指什么）
- 代码命名与领域词汇的对应关系（类名 ↔ 业务概念）

## 质量标准

文档必须详细到：一个**从未读过源码**的人能够——
- 理解模块做什么、为什么这样设计
- 精确定位特定功能在哪里
- 不先通读源码就能做出有依据的修改

不许产出空泛概括。每条论断必须引用具体函数名、类型名或文件路径。

## 反偷懒规则

- 必须读模块内每个文件，不只读"主要"文件
- 必须写出具体函数名和文件路径，不许"有个函数做……"
- 必须解释设计决策，不只描述代码做了什么
- 不确定的地方写"待进一步调查"，不许含糊猜测
