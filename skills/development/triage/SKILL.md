# Triage

把工单推过一个由 triage 角色构成的小型状态机。本仓库的工单跟踪默认是**本地 markdown**：工单文件位于 `.adev/<feature-slug>/issues/<NN>-<slug>.md`。新进来、尚未归类的报告统一放在 `.adev/inbox/issues/` 下。（若 `/setup-dev-workflow` 配置了真实 issue tracker，同一套角色与状态机照样适用，只是"打标签/评论"换成平台原生操作，此处不展开。）

开始时读取 `.adev/agents/issue-tracker.md`、`.adev/agents/triage-labels.md` 与 `.adev/agents/verification.md`。缺少配置先提示用户运行 `/setup-dev-workflow`。标签文档映射下列规范角色到实际存储名称；默认使用既有角色名。

**外部 PR 入口默认关闭。** 只有真实 tracker 配置明确启用后才发现外部 PR，按配置定义“外部贡献者”；显式指定 PR 时可处理该 PR，不自动开启常规发现。本地 markdown 不引入 PR 入口。PR 是附带代码的请求，读取正文、评论、作者、标签和 diff；列表逐项标记 `[PR]` / `[工单]`。PR 的简报说明现有 diff 还需完成什么，`ready-for-human` 可表示已待人工合并，不授权自动合并。

本地约定：

- **"打标签"** = 在工单文件头部写角色行：`**分类：** <category>` 与 `**状态：** <state>`。
- **"评论"** = 在工单文件**末尾**追加一个带日期的章节（见下方模板），不改动已有内容。
- **"关闭"** = 把 `**状态：**` 改为 `wontfix` 并追加结论章节。

triage 期间追加到工单文件的每个章节都**必须**以这行开头：

```
> *本段由 AI 在 triage 过程中生成。*
```

## 角色

两个**分类**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等报告者补充信息
- `ready-for-agent`：已定义清楚，agent 可以开始实现；仍需用户手动验收与代码审查
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

分诊阶段的工单应当恰好带一个分类角色和一个分诊状态角色（即头部同时有 `**分类：**` 和 `**状态：**` 两行）。进入实现生命周期的 `in-progress` / `awaiting-verification` / `done` 按 tracker 约定读取，不作为分诊角色冲突。分诊阶段如果出现冲突（多行、状态角色不止一个），先标记出来并询问维护者，再做别的。

这七个角色名是规范词汇，写入工单或 tracker 时遵循 `.adev/agents/triage-labels.md` 映射。完成状态按 tracker 配置记录，不把 `ready-for-agent` 当作完成。

状态流转：无角色行的工单通常先进入 `needs-triage`；从那里走向 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以覆盖；遇到看起来不寻常的流转，先标记并询问再继续。

## 调用方式

维护者调用 `/triage` 并用自然语言描述想做什么，你来解读并执行。例如：

- "看看有什么需要我处理的"
- "看看 inbox 里那个通讯超时的报告"
- "把 `.adev/inbox/issues/03-xxx.md` 移到 ready-for-agent"
- "现在有哪些可以交给 agent 做的？"

## 展示需要处理的工单

扫描 `.adev/*/issues/*.md`，按三个桶呈现，最旧的在前：

1. **无角色行**：从未 triage 过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次 triage 记录之后报告者有新活动**（文件被报告者编辑过、或对话里有新回复）：需要重新评估。

显示数量和每个工单的一句话摘要，让维护者挑选。

## Triage 一个具体工单

1. **收集上下文。** 通读整个工单文件（正文、所有已追加的章节、日期）。解析已有的 triage 记录，避免重复问已解决的问题。借助项目领域词汇表探索代码库，尊重相关区域的 ADR。对代码库做两项检查：(a) **冗余**：按领域概念（而非报告的措辞）搜索所请求行为是否已有实现，并报告你查了哪些地方。若已实现，走"already implemented 的 `wontfix`"（第 5 步）。(b) **先前拒绝**：读 `.adev/out-of-scope/*.md`，找出与本请求相似的条目。

2. **给出建议。** 告诉维护者你的分类与状态建议及理由，外加与请求相关的代码库简要说明（含是否已实现）。等维护者指示。

3. **先验证再 grilling（verify-before-grill）。** 在任何 grilling 之前，先核实声明是否成立。对 bug，按报告者的步骤实际运行程序复现：启动应用、操作相关界面、观察现象与日志。无运行环境或设备时，请用户执行同一组步骤并反馈，不把代码推断当作复现。对 PR，检出 diff 并编译，按约定手动核实其声明；仅用户明确要求时新增自动化测试。报告结果：已确认（附代码路径）、复现失败、或细节不足（这是强烈的 `needs-info` 信号）。一次已确认的验证会让 agent 简报有力得多。

4. **Grilling（如需要）。** 请求还需要充实成形时，调用 Skill 工具两次——"grilling" 和 "domain-modeling"——一轮一轮地提问把它打磨成形，随时打磨领域术语，决策落地时按领域配置同步更新当前上下文词汇表与 ADR。

5. **落结论：**
   - `ready-for-agent`：追加一份 agent 简报（模板见下）。
   - `ready-for-human`：结构与 agent 简报相同，但注明为什么不能委托（需要人工实施、尚缺外部权限等；正常的手动验收关卡不单独构成 ready-for-human 理由）。
   - `needs-info`：追加 triage 记录（模板见下）。
   - `wontfix`：改状态为 `wontfix`，结论章节的内容取决于**原因**：
     - **已实现**：改动已存在于代码库中。指出它在哪里；**不要**写入 `.adev/out-of-scope/`（那个知识库是给*被拒绝*的请求的，不是给已建成的功能的）。
     - **拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.adev/out-of-scope/`，在结论章节里引用该文件，然后关闭（见下）。
   - `needs-triage`：写入角色行。如有阶段性进展，可选地追加一段说明。

## `.adev/out-of-scope/` 知识库

`.adev/out-of-scope/` 目录记录**被拒绝的 enhancement 概念**，一个概念一个 markdown 文件（`<concept-slug>.md`），同类请求归入同一文件。每个文件写清：概念、拒绝理由，以及历次请求引用。理由应解释范围、架构或方向冲突；暂时没时间是延期，不是永久拒绝。triage 的第 1 步(b) 读它来发现"这个以前拒绝过"；拒绝一个 enhancement 时把新条目写进去。它只管拒绝，不记录已实现的功能。匹配靠领域概念而非关键词；发现相似记录时让维护者选择维持、重新考虑或认定不同。维持则追加本次请求引用；重新考虑则更新或移除旧拒绝记录，新请求继续分诊，不自动重开旧工单。

## 快速状态覆盖

维护者说"把某工单移到 ready-for-agent"时，信任他，直接写角色行。先确认你要做的动作（改角色行、追加章节、关闭），然后执行。跳过 grilling。若未经 grilling 就移到 `ready-for-agent`，问一句是否要补一份 agent 简报。

## Triage 记录模板（needs-info）

在工单文件末尾追加：

```markdown
---

## YYYY-MM-DD Triage 记录

> *本段由 AI 在 triage 过程中生成。*

**目前已确认的：**

- 要点 1
- 要点 2

**还需要你提供（@报告者）：**

- 问题 1
- 问题 2
```

grilling 中解决的一切都要收进"目前已确认的"，不让工作成果丢失。问题必须具体、可回答，不要写"请提供更多信息"。

## Agent 简报模板（ready-for-agent / ready-for-human）

在工单文件末尾追加：

```markdown
---

## YYYY-MM-DD Agent 简报

> *本段由 AI 在 triage 过程中生成。*

**目标：** 一句话说清要达成什么，从用户视角描述，而非实现清单。

**当前行为：** 现在发生什么；PR 描述现有 diff 的完成情况与缺口。

**期望行为：** 完成后应发生什么，涵盖边界与错误情况。

**关键接口：** 按领域类型、行为契约说明哪些接口需变化，不给易过时的文件路径或行号。

**Spec：** <已存在的 spec 路径或 tracker 引用；若本简报本身就是实现规格，明确引用这份持久化简报>

**已确认的事实：**

- 验证与 grilling 中确认的、实现者无需再查的事实：复现路径、按领域概念描述的相关代码位置、已排除的方向

**约束：**

- 必须遵守的 ADR、领域术语约定、兼容性要求

**范围之外：** 本工单不修改的相邻行为。

**验收方式（手动验证步骤）：**

- [ ] 启动什么 / 操作哪个界面 / 观察什么现象 / 预期结果
- [ ] ……
```

要点：

- 简报要**耐久**：agent 拿到它时不带本次对话的任何上下文，所有必需信息必须写在简报或它指向的文档里。
- "已确认的事实"只写核实过的内容；没核实的写进"约束"或直接删掉，别让实现者把猜测当事实。
- 验收方式一律是**用户可执行的手动验证步骤**（启动程序、操作界面、观察现象与预期结果），仅用户明确要求时才新增自动化测试。工控项目可涉及仿真器或真实设备；纯桌面端不得包含硬件前提。

## 恢复之前的会话

工单文件里已有 triage 记录时，先读它，检查报告者是否已答复未决问题，给出更新后的全貌再继续。不要重复问已解决的问题。
