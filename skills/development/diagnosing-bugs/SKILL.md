# 诊断 Bug

针对疑难 bug 的纪律。只有明确理由才能跳过阶段。

探索代码库时，先读 `CONTEXT.md`（如存在）建立相关模块的心智模型，并查看所触及区域的 ADR。

## 脱敏

本 skill 会让你展示命令、输出和捕获的工件。**先脱敏**：密钥一律写 `<REDACTED>`。连接串、设备 IP、授权码出现在日志/报文里时，只引用携带信号的行。脱敏后的输出不足以诊断时，明说并问用户。

## 阶段 1：建立反馈闭环

**这是本 skill 的核心。** 其余都是体力活。有了对这个 bug 会变红的**紧致**通过/失败信号，原因一定能找到——二分、假设检验、插桩都只是消费它。没有它，盯着代码看多久都没用。

在这里投入不成比例的精力。**要激进，要有创造力，拒绝放弃。**

### 构造闭环的手段（大致按此顺序，C# 桌面端语境）

1. **调试器断点 + 复现步骤**：Visual Studio 断点/条件断点/数据断点，配合最短复现路径。
2. **日志/报文捕获回放**：把真实通信报文、事件日志存盘，在隔离的代码路径里回放（如把一帧 Modbus 报文直接喂给解析函数）。
3. **仿真器复现脚本**：用仿真器（Modbus 仿真、PLC 仿真）构造稳定触发工况，让 bug 按需出现。
4. **版本二分**：bug 出现在两个已知状态（commit、版本）之间时，自动化"检出状态 X → 启动 → 检查"以便 `git bisect`。
5. **差异对比**：同一输入跑旧版本与新版本（或两套配置），diff 输出。
6. **一次性线束**：搭一个最小子系统（单个类 + mock 依赖），一次调用走完出 bug 的代码路径。
7. **HITL 脚本**：兜底。必须人点界面时，把步骤写成结构化清单驱动用户操作，捕获的输出发回给你。

闭环搭对，bug 就修好了 90%。

### 收紧闭环

把闭环当产品打磨：

- 能更快吗？（缓存准备工作、跳过无关初始化、缩小范围）
- 信号能更尖锐吗？（断言具体症状，而不是"没崩"）
- 能更确定吗？（固定时序、隔离文件系统、冻结外部输入）

30 秒还不稳定的闭环约等于没有；2 秒确定性的闭环是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**：循环触发 100 次、并发、加压、收窄时序窗口、注入延时。50% 的 flaky 可调试，1% 不行——持续提升复现率直到可调试。

### 实在建不出闭环时

停下来明说。列出试过的手段。向用户要：(a) 能复现的环境的接入方式，(b) 脱敏后的捕获工件（日志 dump、报文抓包、带时间戳的录屏），或 (c) 临时加生产插桩的许可。**不要在无闭环的情况下开始假设。**

### 完成标准：一个紧致且可变红的闭环

阶段 1 完成的标志：你能说出**一个操作**（脚本路径、一次调试器会话、一组复现步骤），且已**至少跑过一次**（展示调用与脱敏输出），它满足：

- [ ] **可变红**：走的是真正的 bug 代码路径，断言**用户描述的精确症状**，能在此 bug 上变红、修复后变绿。不是"跑完没报错"，而是能**抓住这个特定的 bug**。
- [ ] **确定**：每次结论一致（flaky bug：按上文固定住足够高的复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **可重复执行**：agent 可无人值守运行；需要人操作时走 HITL 脚本。

如果你发现自己在闭环存在之前就开始读代码构建理论，**停：直接跳假设正是本 skill 要防止的失败。** 没有可变红的操作，不进阶段 2。

## 阶段 2：复现 + 最小化

跑闭环，看它在 bug 出现时变红。

确认：

- [ ] 闭环产生的失败模式是**用户描述的**那个，不是碰巧在附近的另一个失败。看错 bug = 修错 bug。
- [ ] 失败可多次复现（非确定性 bug：复现率足够高）。
- [ ] 已捕获精确症状（报错信息、错误输出、异常耗时），供后续阶段验证修复确实对症。

### 最小化

变红后，把复现收缩到**仍然变红的最小场景**：输入、调用方、配置、数据、步骤**一次砍一个**，每砍一刀重跑闭环，只留下对失败承重的部分。

为什么值得：最小复现缩小阶段 3 的假设空间（剩下的活动部件更少），并成为阶段 5 干净的回归验证步骤。

完成标准：**剩下的每个元素都承重**——去掉任何一个闭环就变绿。

未复现且未最小化，不继续。

## 阶段 3：假设

先产出 **3–5 个排序后的假设**，再检验其中任何一个。只产一个假设会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：写出它的预言。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。"

写不出预言的假设是玄学：丢弃或磨尖。

**检验前把排序后的列表给用户看。** 用户常有领域知识能瞬间重排（"3 号我们昨天刚动过"），或知道哪些已排除。便宜的检查点，省大量时间。不要阻塞等回复：用户不在就按你的排序继续。

## 阶段 4：插桩

每个探针必须对应阶段 3 的某个具体预言。**一次只改一个变量。**

工具偏好：

1. **调试器 / 即时窗口**：环境支持就优先。一个断点胜过十条日志。
2. **定点日志**：打在能区分假设的边界上。
3. 绝不"全量打日志再 grep"。

**每条调试日志都带唯一前缀**，如 `[DEBUG-a4f2]`。收尾时一次 grep 即可清干净。未标记的日志会活下来，带标记的才会死。

**性能分支。** 性能回退时日志通常是错的工具。改为：先建立基线测量（计时线束、性能计数器、profiler），再二分。先测量，后修复。

## 阶段 5：修复 + 回归验证

**本工作流不写自动化回归测试。** 改为：

1. 应用修复。
2. 重跑阶段 1 的闭环，确认变绿。
3. 用**原始（未最小化的）场景**再跑一遍，确认真实场景也绿了。
4. 把最小复现整理成**手动回归验证步骤**（启动什么/操作什么/预期观察什么），交给用户按 `docs/agents/verification.md` 的约定实际运行确认；工控项目注明需要仿真器还是真实设备。
5. 把验证步骤连同正确假设记录到对应工单（或 `docs/agents/` 下的调试记录），供以后回归时复用。

**如果发现 bug 根本无法在不连真实设备的情况下复现或验证**，这本身是发现：代码缺少可注入的 seam（如通信层被硬编码）。记录下来，这是 `/improve-codebase-architecture` 的输入。

## 阶段 6：收尾

宣布完成前必须：

- [ ] 原始复现不再出现（重跑阶段 1 闭环）
- [ ] 用户已按手动验证步骤确认通过
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试目录）
- [ ] 正确的那个假设写进了提交信息，让下一个调试者能学到
