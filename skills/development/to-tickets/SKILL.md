# To Tickets

把计划、spec 或对话拆成一组**工单**：tracer-bullet 式的纵向切片，每个声明哪些工单**阻塞**它。

工单跟踪方式应当已由 `/setup-dev-workflow` 配置好。如果没有，提示用户先运行 `/setup-dev-workflow`。

## 流程

### 1. 收集上下文

利用对话中已有的内容。用户传了引用（spec 路径、工单号）作为参数时，取回并通读全文。

### 2. 探索代码库（可选）

还没探索过则探索。工单标题和描述使用项目领域词汇，尊重所触及区域的 ADR。

留意**预重构**机会：让后续实现变容易的先行改动。"先让改动变容易，再做容易的改动。"

### 3. 草拟纵向切片

把工作拆成 **tracer bullet** 工单：

- 每个切片切出一条**窄而完整**的通路，穿过各层（通信层 → 业务逻辑 → UI）：是纵向切片，不是某一层的横切
- 完成的切片**可独立手动验证**：用户能启动程序、操作界面、观察到这条通路的行为
- 每个切片大小以**一个全新上下文窗口能装下**为准
- 预重构排在最前

给每个工单声明**阻塞边**：必须先完成的其他工单。无阻塞的工单可立即开始。

**宽重构是纵向切片的例外。** 一次机械改动（改公共协议结构、重命名共享类型）波及全代码库、任何纵向切片都无法独立落地时，按 **expand–contract** 排：先扩展（新旧并存、不破坏任何调用点），再分批迁移（每批一个工单、保持可编译），最后收缩（删除旧形式）。

### 4. 与用户核对

以编号列表展示拆分方案。每个工单给出：

- **标题**：简短描述
- **阻塞于**：哪些工单必须先完成
- **交付什么**：这个工单让哪条端到端行为可用、用户怎么验证

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边对吗？每个工单只依赖真正卡住它的工单吗？
- 有该合并或该再拆的吗？

迭代到用户认可。

### 5. 发布工单

按 `/setup-dev-workflow` 配置的方式发布：

- **本地 markdown**（默认）→ 在 `.scratch/<feature-slug>/issues/` 下每工单一个文件，命名 `<NN>-<slug>.md`，从 `01` 起按依赖顺序编号（阻塞者在前）。用下面的本地模板：一工单一个文件，绝不合并成一个文件。
- **真实 issue tracker** → 按依赖顺序逐条创建 issue，用平台原生的阻塞/子任务关系；没有则在 "Blocked by" 里引用阻塞工单。

按 **frontier** 推进：所有阻塞项都完成的工单就能开工。纯线性链就是从头做到尾。

不要关闭或修改任何父工单。

## 验收标准（手动验证步骤）

- [ ] 步骤 1：启动/操作/预期观察
- [ ] 步骤 2：……

</local-ticket-template>

验收标准必须写成**用户可执行的手动验证步骤**：写什么动作、看什么界面/日志/设备现象、预期结果是什么。不要写成自动化测试的断言。

避免具体文件路径和代码片段，它们很快过时。例外同 to-spec：决策密度高的小片段可以内联并注明来源。
