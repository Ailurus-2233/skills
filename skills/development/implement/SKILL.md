# Implement

实现用户指定的 spec 或工单。

本工作流面向 C# 工控桌面端，**验收靠用户手动运行程序，不靠自动化测试**。

## 硬性约束

- **不要创建单元测试项目、测试代码或任何"自动检查是否完成"的脚本**，除非用户明确要求。
- **允许且应该**做编译检查：`dotnet build`（或在用户 IDE 不可用时等价命令）确认无编译错误。编译是基本卫生，不是验收。
- 不要用"代码看起来对"代替用户验证。**完成与否由用户运行程序后确认。**

## 流程

1. **明确任务来源**：一个工单、一份 spec，或对话中刚达成一致的方案。工单来自 `.scratch/` 或工单跟踪处时，通读全文，确认它的阻塞项均已完成。

2. **切分实现片段**：把工作分成若干个可独立验证的片段（通常一个片段对应工单的一到两条验收标准）。每个片段都应该是"改完用户就能运行看到点什么"的最小单位。

3. **逐片段实现**，每个片段完成后：

   a. 编译检查通过。
   
   b. **停下来**，向用户报告：
   
   ```
   ✅ 片段 <N> 已完成：<一句话说明改了什么行为>
   
   修改的文件：<文件列表及各自改动要点>
   
   请按以下步骤验证：
   1. <启动/操作步骤>
   2. <观察哪个界面/日志/设备现象>
   3. 预期结果：<具体可观察的结果>
   
   验证通过后回复确认；不符合预期请描述实际现象。
   ```
   
   验证步骤遵守 `docs/agents/verification.md` 的约定（验证环境、启动方式、日志位置）。
   
   c. **等用户反馈**：
   - 通过 → 勾选工单对应验收标准，进入下一片段
   - 不通过 → 根据用户描述的实际现象修复，修复后**重新给出同一组验证步骤**，再等确认

4. **工单收尾**：全部验收标准经用户确认后，更新工单状态；按仓库提交惯例提交到当前分支（提交信息引用工单号）。多个工单时提示用户：下一个可开工的工单（阻塞项已完成的）有哪些，建议新开会话实现。

## 注意

- 一片段一停顿，不要积攒多个片段才让用户验证——验证成本随批量上升，返工成本也是。
- 用户反馈"不通过"时，优先让用户描述现象、提供日志/报文截图文字，而不是自己猜测修改方向。
- 实现中发现 spec/工单与现实冲突，停下来向用户说明冲突点，不要静默按自己的理解继续。
