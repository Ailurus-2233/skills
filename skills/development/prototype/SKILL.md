# Prototype

原型是**用完即弃、只为回答一个问题而写的代码**。问题决定原型的形态。

## 选一个分支

先弄清要回答的是哪个问题——根据用户的描述、周边代码判断，用户在就直接问：

- **"这个逻辑 / 状态模型跑得通吗？"** → 逻辑原型。写一个**最小控制台程序**（或单文件脚本式 demo），把状态机推过那些在纸上难以推理的用例，并在每一步打印完整的相关状态。交互方式保持最简：循环读输入触发事件、随即打印状态转移，或按固定脚本顺序跑完整组用例。
- **"这块界面该长什么样？"** → UI 原型。在**主程序的一个窗口/页面内**做几套差异明显的方案，通过一个入口切换（如按 Tab 键、命令行参数或一个明显的原型切换控件）。方案之间要有真实差异（布局、导航结构、信息层级），不是微调配色。

两个分支的产物形态完全不同，选错分支整个原型就白费了。如果问题确实模糊且用户联系不上，默认按周边代码判断（纯服务/通讯/逻辑模块 → 逻辑分支；窗口、页面、控件 → UI 分支），并在原型开头写明这个假设。

## 两个分支通用的规则

1. **从第一天起就是用完即弃，并且一眼能看出来。** 把原型代码放在靠近它真正要服务的模块旁边（同项目里的原型文件夹、或同名带 `Prototype` 后缀的文件/窗口），让上下文显而易见；但命名要让随便翻看的人立刻知道这是原型、不是生产代码。UI 原型遵守项目已有的窗口/导航组织方式，不要发明新的顶层结构。
2. **一键就能跑。** 逻辑原型是一个 `dotnet run` 即可启动的控制台项目，或一个能直接跑的单文件脚本；UI 原型随主程序启动即可看到（或用参数指定进入）。启动前不需要任何思考。
3. **默认无持久化。** 状态只活在内存里。持久化正是原型要*验证*的东西，不是原型应该依赖的东西。如果问题明确涉及数据库或文件，用一个名字清楚标注"原型，随时可删"的临时文件或临时库。
4. **不做打磨。** 不写自动化测试，不做超出"能跑起来"所需范围的错误处理，不做抽象。验收靠用户按手动验证步骤运行确认——给原型的验证步骤同样遵循"启动什么 / 操作哪个界面 / 观察什么 / 预期结果"的写法。
5. **把状态暴露出来。** 逻辑分支：每次动作之后打印完整的相关状态；UI 分支：每次切换方案后让用户能直接看到这块界面在真实数据下的样子。用户要能看到"发生了什么变化"。
6. **完成后作为 primary source 捕获。** 把验证通过的结论折叠进正式代码，然后把原型本身作为**一手资料**保留：提交到一个 `prototype/<name>` 的用完即弃分支（不进主干），并在实现工单（`.scratch/<feature-slug>/issues/` 下的本地工单，或真实 tracker）上留下指向该分支的指针。答案也要记下来（结论和它回答了什么问题）——写在工单或提交信息里。主干只保留验证通过的决策本身。
