# Implement Spec

仅在用户显式调用 `/implement-spec` 时执行；日常逐工单实现仍使用 `/implement`。

读取真实存在的 spec、关联工单及 `.adev/agents/issue-tracker.md`、`.adev/agents/verification.md`。缺少配置先提示用户运行 `/setup-dev-workflow`；找不到 spec 时请用户指定，不以会话内容代替。目标是整份 spec 在一个集成分支上完成，工单全部经过用户验收与代码审查。

## 权威上下文与状态

工单组成依赖图。**frontier** 是所有阻塞工单均完成、且未被认领的工单；完成指所有片段验收与审查通过。

`.adev/` 被忽略，不会随 Git worktree 自动复制。开始时确定原工作区中 spec、工单、验证约定和领域文档的绝对路径，作为所有子 agent 共享的唯一权威副本；传递这些路径，不在各 worktree 创建副本。主 agent 独占工单状态、认领、验收勾选和完成记录的写入；子 agent 只读取并报告。真实 tracker 同样由主 agent 更新状态。

子 agent 的任务以 spec、工单、当前片段、集成分支提交和文档指针描述，不复制整份上下文。新分支使用项目约定的前缀。

## 执行

1. **建立基线。** 通读 spec、全部工单和依赖，确认每个片段能独立编译并手动验证。宽重构采用 expand–contract；不能独立编译的片段合并，不留到最终批次才编译。记录审查基准，创建集成分支。

2. **派发一批片段。** 从当前 frontier 及本次执行已认领、上一批已通过但尚有片段的工单中选择，每张工单只派发下一个未验收片段。给各实现子 agent 创建独立分支和 worktree，基于本批次开始时的集成分支提交。主 agent 记录认领；同一工单不重复派发。子 agent 读取共享绝对路径，实施指定片段并编译，报告提交和手动验证步骤后停止。默认不新增测试项目、测试代码或自动化验收脚本；只有用户明确要求才新增，编译不能代替手动验收。

3. **集成并编译。** 主 agent 将本批片段逐一合入集成分支，解决冲突并编译。未编译通过时继续修复，不能请求用户验收或派发下一批。集成冲突改变行为时同时更新该片段的验收步骤。

4. **集中手动验收。** 向用户逐片段列出改动、启动方式、操作、观察点和预期结果，明确运行的是集成分支。等用户反馈，不能用子 agent 的编译结果或自评勾选验收。失败的片段先修复、编译，再请求复验；本批全部通过后才能继续派发。工单仍有片段时，下批推进这些片段；不提前解锁其依赖。

5. **完成工单再推进依赖。** 某工单全部片段已验收时，主 agent 调用 `code-review` 审查其累计变更，提供真实 spec、工单和准确 Git 范围。修复后编译并复核审查；行为改变须重新手动验收。通过后主 agent 标记该工单完成、解除认领，再计算 frontier，返回第 2 步。不得把“已合入”当作完成。

6. **整体验证与交付。** 全部工单完成后，对集成分支相对起始基准做一次整体 `code-review`，检查跨工单配合与整份 spec。处理发现的问题，编译并重新验收受影响行为，再复核审查。全部通过才完成 spec；调用 `commit-message` 为尚未提交的最终修复生成提交信息并提交。只有本次任务已授权创建 PR 时，才在首次有集成提交后创建草稿，最终验收与审查通过后标记可审查；遵守 tracker 的关闭方式，不把等待合并的事项提前关闭。若 tracker 需要 PR 而本次未授权发布，交付集成分支与 `/pr` 生成的草稿正文，保留待发布状态；其他情况记录完成状态并交付集成分支。

7. **清理。** 确认子 agent 的提交已集成，所需资料均留在权威位置，再清理本次创建的 worktree。报告分支、工单状态、编译结果和用户验收记录。
