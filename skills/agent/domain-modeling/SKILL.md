# 领域建模

在设计过程中主动构建并打磨项目的领域模型。这是*主动*的纪律：质疑术语、编造边界场景、在术语与决策定型的一刻就把它们写下来。（仅仅*读* `.adev/GLOSSARY.md` 查词汇不算本 skill：那是任何 skill 都该有的顺手习惯。本 skill 管的是你在改动模型，而不只是在消费它。）

## 文件结构

先读 `.adev/agents/domain.md` 确认布局。多数仓库使用 `.adev/GLOSSARY.md` 与 `.adev/adr/`。多上下文使用 `.adev/GLOSSARY-MAP.md`，指向 `.adev/contexts/<context>/GLOSSARY.md` 和 `.adev/adr/<context>/`；所有工作流文档均留在根部 `.adev/` 内。先确定当前话题所属上下文，无法判断时询问；以下“当前词汇表”指配置/索引选定的那一份文件，多上下文时不另建单上下文词汇表。

按需创建：第一个术语敲定时才创建词汇表，第一份 ADR 需要落笔时才创建 ADR 目录。文件不存在就继续，不先生成空文档。旧的 `CONTEXT.md` / `CONTEXT-MAP.md` 按 `setup-devenv` 的迁移流程处理，避免新旧两套词汇同时维护。

## 会话进行中

### 对照词汇表质疑

用户用的词与当前词汇表里的既有语言冲突时，立刻指出："你的词汇表把'取消'定义为 X，但你刚才的意思似乎是 Y。到底是哪个？"

### 打磨模糊语言

用户用词含糊或一词多义时，提出一个精确的规范术语："你说'账户'，指的是客户还是用户？这是两个东西。"

### 讨论具体场景

讨论领域关系时，用具体场景做压力测试。编造能探到边界的场景，逼用户把概念之间的界线说精确。

### 与代码交叉核对

用户陈述某物如何工作时，检查代码是否一致。发现矛盾就摆出来："你的代码会取消整张工单，但你刚才说可以部分取消。哪个是对的？"

### 就地更新当前词汇表

术语一敲定，当场更新当前词汇表。不要攒批：随发生随记录。只收录本项目领域特有的概念，不把通用编程术语写进词汇表；同一概念选定一个规范名称，在“避免”中列出误用词。自然形成多组时再分小节。格式如下：

```markdown
# <上下文名称>

<一两句话说明范围。>

## 领域语言

**术语**：定义（一两句话，只讲领域含义）。

_避免_：同义误用词（说明它常被错当成这个术语）。
```

当前词汇表必须完全不含实现细节。不要把它当规格书、草稿纸或实现决策的仓库。它只是词汇表，别无他物。

### 克制地提供 ADR

只在以下三条全部成立时，才提议创建 ADR：

1. **难以逆转**：日后改主意的代价是实打实的
2. **缺了上下文会让人费解**：未来的读者会纳闷"他们当时为什么这么做？"
3. **真实权衡的结果**：确实存在过像样的备选方案，而你因为具体理由选了其中一个

三条缺任何一条，就跳过 ADR。在对应 ADR 目录中扫描已有最大编号，使用下一个 `NNNN-slug.md`。默认只写标题和 1–3 句话：

```markdown
# <决策标题>

<背景约束是什么；决定做什么；为什么这样选。>
```

只有能帮助后续理解时才加状态、备选方案、后果等小节。复杂设备、协议或不可逆迁移决策可以充分展开；不为填满模板重复信息。

工作分类 ADR 是用户工作流要求的索引，不受上述“是否值得新建决策 ADR”的筛选限制。按 `.adev/agents/issue-tracker.md` 维护其工作目录链接与当前状态摘要；关联具体工作的其他 ADR 也链接实际工作目录及分类 ADR 的状态索引。工作状态由工单与验证证据汇总，不能混同 ADR 决策本身的采纳/废弃状态，也不在多份 ADR 复制维护状态。
